## 三、环境阻塞（实测量化）

### 1. 硬件级 fp16 缺陷（致命）
`torch.cuda.amp` 的 fp16 autocast 路径在本机 **必然产生 NaN**，根因已定位到单个算子：

```
conv1 (k=19,s=4, 1→64)   fp16 有限 ✅
conv2 (k=11,s=4,64→64)   fp16 → NaN ❌   <-- 全网络第一个非有限值
conv3 (k=7, s=1,64→64)   fp16 有限 ✅
```

- 与 batch size（32→20480）、输入幅度（×1.0 / ×0.02）均无关；
- `torch.backends.cudnn.enabled=False` 后 fp16 恢复正常 → **cuDNN 9.10.2 在 TU116（GTX 1660 SUPER）上 `Conv1d(64,64,k=11,s=4,p=5)` 的 fp16 kernel 有缺陷**。
- 附带发现：关闭 cuDNN 后 fp16 反而慢 5 倍（bs=256 时 3.07 s/step vs fp32+cudnn 0.27 s/step），所以「关 cuDNN 换 fp16」不划算。

**处置：改用 fp32 + cuDNN，禁用 autocast/GradScaler。** 论文未提混合精度，fp32 更贴论文口径。

### 2. `torch.load` 失败（阻塞）
`train_active_learning.py` / `test-pretrained-model.py` 用 `torch.load(path)` 直接加载 `list[nn.Module]`。
torch ≥2.6 默认 `weights_only=True` → `UnpicklingError`。必须显式 `weights_only=False`。

### 3. 精确实测的显存/速度预算（fp32 + cuDNN + benchmark）

| batch | s/step | samples/s | 峰值显存 | 等效 batch=1024 |
|---|---|---|---|---|
| 64 | 0.0675 | 948 | 3.41 GB | 1.08 s |
| **128** | **0.1309** | **978** | **1.91 GB** | **1.05 s** |
| 192 | 0.2042 | 940 | 2.86 GB | 1.09 s |
| 256 | 0.2651 | 966 | 3.80 GB | 1.06 s |
| 384 | 0.9710 | 395 | 5.69 GB | 2.59 s（开始溢出） |
| 1024（原设定） | 6.01 | 170 | **8.61 GB > 6GB** | **溢出到内存，慢 10 倍** |

**结论：论文的 batch=1024 在 6 GB 卡上必然溢出主机内存；必须用 micro-batch 128 或 256 + 梯度累积。**
吞吐稳定在 ~975 samples/s，这是全部时间预算的基准。

### 4. 时间预算（SleepEDF-20 全 10 折）
单折训练集 ≈ 40,400 样本 → 41 s/epoch → 200 epoch = 2.3 h/折 → **10 折 ≈ 23 h**；UGAL 阶段（每折 4 条测试录音，各自微调 200 epoch）≈ 1 h。**合计约 24 h。**

## 四、论文 ↔ 代码差异（关键，影响能否复现出论文数字）

| # | 论文 | 代码实际 | 影响 |
|---|---|---|---|
| A1 | Eq.10：`H=-Σ μ^α σ^(1-α) log μ`，α=0.5 | `tools.py` 三处不一致：`experts_set_quantified_uncertainty` 用 `(σ/μ)^1`；`test_quantified_uncertainty` 用 `(σ/μ)^0.7`；`train_active_learning.py` 实调的是 **纯熵** `test_entropy_uncertainty`，完全不含贝叶斯项 | **核心方法不一致**，论文的「quantified uncertainty」未真正被使用 |
| A2 | `QU(x)=H(y1)+H(y2)`，取**预测熵加权** | 一致（两专家熵相加） | — |
| A3 | 门控权重 `w_i=softmax(-H_i)`（Eq.11/12），加权融合 | `output_multi_models` 是 `Σ μ_i/σ_i` 归一化后直接相加，**没有 softmax 门控**；评测里是 `Σ μ_i/H_i` | 融合公式与论文不符 |
| A4 | 两专家在**互斥数据分片** D1/D2 上独立训练，D1∪D2=D | `train-pretrained-model.py` 用**同一份完整训练集**、`train_epoch` 里按 batch **轮流只更新一个模型**，且 `pi/=2` 逐 batch 衰减 KL 权重 | 集成的多样性来源消失 |
| A5 | MC 前向 **N×T=200 次**（每专家 T=100） | Stage-1 选样只做 **50 次**（每专家 25）；Stage-2/测试才用 200 | 选样阶段不确定性噪声偏大 |
| A6 | 对所有未标注样本**全局按 QU 升序排序**，每 k 个取 1 | DataLoader `shuffle=True`，**在随机 batch 内（1024）各自排序**，非全局 | 系统性采样的分布不同 |
| A7 | α 固定 0.5，`Fully Connected(64→5) + Softmax` | 输出用 `F.sigmoid` 再除以和（`influence()`）；`test_entropy_uncertainty` 还对已归一化的概率**再做一次 softmax**（双重 softmax） | 概率语义偏移 |
| A8 | 表 I 写 `BiLSTM(64)` | 代码 `LSTM(bidirectional=False)` | **代码是对的**：单参数 265,536 → ×2 = **531,072 = 论文 5.3×10⁵**，若双向会变 396k。判定为论文表格笔误 |
| A9 | 输入「Raw EEG segment」 | `model.forward` 里做**跨整个 batch** 的 z-score：`mean(x, dim=(0,2))`，即用一批 1024×20 个片段共同算 1 个均值/方差 | 归一化依赖 batch 组成，评测结果随 batch/shuffle 波动；复现时需注意 |

### 工程教训：受管后台通道是唯一可靠的长任务载体

本环境里长任务的存活只有一种可靠方式：**受管后台任务通道**。
- `nohup` / `Popen(DETACHED_PROCESS)` / `start` 都不行——工具调用一返回，子进程即被回收
  （两次实测：pid 11980、pid 16460 均在启动后数秒内消失）
- **推论**：`repro/queue_after_main.py` 用 `Popen` 拉起的消融会被连带清理。
  看门脚本本身逻辑正确（`2026-09-22 03:18:33` 准确识别 `summary.json` 并发出启动），
  但**接力启动的子进程不具备存活能力**，已改为手工用受管通道启动。
  若将来要修，应让看门脚本用受管通道启动，或把「等待 + 启动」合并进同一个受管任务。
- 另注：主任务结束时管理侧报 `failed`，但 `summary.json` 与完整 `run.log` 均已写出，
  属退出码误报，非任务失败。

## 十、并行跑消融的实测结论：**放弃并行，改为排队接力**

### 1. 消融口径选定

原始代码的消融定义（`train-pretrained-model.py:25-32` 等三处一致）：

| 论文 Table IV 行 | 原始配置 | 对应 `repro/run.py` 参数 |
|---|---|---|
| w/o ensemble | `bayesian=T, mc_drop=T, model_num=1` | `--models 1` |
| w/o Bayesian conv | `bayesian=F, mc_drop=T, model_num=2` | `--bayesian 0` |
| w/o MC dropout | `bayesian=T, mc_drop=F, model_num=2` | `--mc-drop 0` |
| Vanilla model | `bayesian=F, mc_drop=F, model_num=1` | `--bayesian 0 --mc-drop 0 --models 1` |

选 **w/o ensemble**（`--models 1`）。

**重要背景**：Table IV 在 SleepEDF-20 上 4 个组件消融彼此差距 ≤0.03 ACC / ≤0.11 MF1，且
`w/o Bayesian conv`(81.22) 与 `Vanilla`(81.23) 的 MF1 **高于**完整模型(81.12)——组件消融本身是
噪声级实验。真正有区分度的是采样策略：86.75 → 91.98(Random) → 94.58(UGAL)。所以组件消融

## 十一、与论文绝对差的归因分析（CV −2.16 / UGAL −1.45）

### 1. 统计量级：CV 的差距不显著

CV 十折 ACC 样本标准差 4.374 → 均值标准误 SE = 4.374/√10 = **1.383**。
差距 2.16 → **t = 1.56，p ≈ 0.153**（df=9），**未达显著**。
UGAL 逐被试 std 3.32 → SE ≈ 0.53，差距 1.45 → t ≈ 2.7（p ≈ 0.02），边缘显著。
（注意 4 个测试被试共享同一预训练模型，被试间不独立，实际有效样本量小于 39。）

### 2. 但形态上不像纯噪声 —— 是「系统性水平位移」

| | 论文 | 本复现 | 差值 |
|---|---|---|---|
| CV ACC | 86.75 | 84.59 | **−2.16** |
| CV MF1 | 81.12 | 78.92 | **−2.20** |
| UGAL ACC | 94.58 | 93.13 | **−1.45** |
| UGAL MF1 | 89.24 | 86.15 | **−3.09** |
| CV→UGAL ΔACC | +7.83 | **+8.54** | — |

CV 与 UGAL **同向偏低且幅度相近**，而两者的**增益几乎完全一致**。
若是纯随机噪声，CV 与 UGAL 会各自独立偏移、符号随机；同向等幅偏置 + 增益守恒
是典型的「模型整体略弱一档」特征 → 指向**口径差异**，而非运气。
（CV 偏低 2.16 = 1.56 SE，单独看不显著；但两个口径同时偏低，联合概率约 0.02 量级。）

### 3. 逐比特复现本来就不可达

`train-pretrained-model.py:75` 只训练 **5 折**（`for fold in range(0, int(np.ceil(folds/2)))`），
而论文报 10 折；`tools.py:115-128` 的训练循环**从不调用 `optimizer.zero_grad()`**
（梯度跨 batch 累积）。这两点说明**论文数字不可能来自这份发布代码**，
必然来自另一份内部实现 → 不存在可逐比特对齐的参照物。

### 4. 已定位的口径差异（附方向判断）

| # | 项 | 原始代码 | 本复现 | 预期方向 |
|---|---|---|---|---|
| 1 | **BN 共享** | 5 个卷积层**复用同一个 `self.bn1`**（`model.py:191/195/206/210/214`） | 5 个独立 BN（论文口径修正 8） | **最大嫌疑**，方向不明 |
| 2 | **输出激活** | `F.sigmoid` 输出直接喂给 `F.cross_entropy`（CE 期望 logits），`model.py:234` | 原始 logits + 正确 CE（修正 1） | 本复现**应更好** |
| 3 | **fp16** | `autocast()` + `GradScaler` | 全 fp32（TU116 cuDNN fp16 缺陷，被迫） | 本复现略差 |
| 4 | KL 权重 | `pi/=2` 每 batch 减半 | 恒定 2e-8（修正 7） | **可忽略**：KL 项 ≈1e-4 vs CE ≈0.2 |
| 5 | zero_grad | 缺失 | 补齐 | 本复现**应更好** |
| 6 | 训练折数 | 仅 5 折 | 全 10 折 | 不可比 |

注意 #2 与 #5 都是「本复现理论上更正确」，却得到更低的结果 —— 说明把差距简单归因于
「我的修正改错了」并不自洽。#1（BN 共享）是唯一方向不明、且量级可能与 2 个点相当的候选。

### 5. 可检验预测：MF1 的差距应集中在 N1

MF1 差距 2.20 × 5 类 = 累计 11.0 个点。本复现 N1 的 F1 最低（CV 49.91、UGAL 58.69），
而 N1 本身就是最难的类别。若差距来自模型整体变弱，**应主要体现为 N1（其次 N3）的 F1 损失**。
论文 Table IV 未公布 per-class F1，故无法直接对照——这是论文报告粒度上的缺口。

### 6. 唯一能定位成因的办法：单折对照实验

继续推理无法收敛，应做受控实验。以 fold 0 为固定折（本复现已有基线 79.84），
单变量改动后各跑 1 折（≈155 min/折）：

| 配置 | BN | 输出激活 | 对应 |
|---|---|---|---|
| A（已有） | 分开 | logits | 当前复现 |
| B | **共享** | logits | 隔离 BN 共享的影响 |
| C | 分开 | **sigmoid+CE** | 隔离输出激活的影响 |
| D | 共享 | sigmoid+CE | 完全对齐原始代码 |

A→B 与 A→C 各一次即可判明主因（2 折 ≈5.2 h）。须排队等消融跑完再跑
（并行是净亏，见第十节）。这需要给 `run.py` 增加 `--share-bn` / `--out-act` 开关。

## 十二、为什么"这么点数据"要跑这么久（算力账本）

实测口径：稳定期 **47.2 s/epoch**（由 `ablate_noensemble_stdout.log` 的
ep161→ep191 即 175m45s→199m27s 推得）。主任务 fold 均 ≈166 min
（fold 0 因探针事故被拖到 298 min），消融 fold 均 157 min。

GPU：GTX 1660 SUPER（TU116，1408 SP，boost 1.785 GHz，**无 Tensor Core**）
→ fp32 峰值 = 1408 × 2 × 1.785e9 = **5.03 TFLOPS**。

### 1. 数据集小 ≠ 计算量小：序列展开带来 20× 冗余

- 35 个训练 recording 共 **39,527** 个 30 s epoch；
- `bsn.py:210 seq_index_matrix` 为**每个 epoch 生成一条序列**（取该 epoch 及其前 19 个拼接，
  前端补零），故每个 epoch 出现在 20 条序列中（i … i+19）；
- `Expert.forward`（`bsn.py:124`）把 `(B, 20, 1, 3000, 1)` reshape 成 `(B*20, 1, 3000)`
  **先整体过 CNN**，再由 LSTM 聚合 → **CNN 是逐 epoch 的**；
- ⇒ 单个训练 epoch 中 CNN 实际处理 39,527 × 20 = **790,540 段**，
  而唯一数据只有 39,527 段，**冗余系数恰为 20**。
- 真正用到序列结构的只有 LSTM，而它只占 1.1% 算力。

### 2. 逐层计算量（单序列，20 epoch）

真实张量顺序是 conv1 → conv2 → pool1 → conv3 → conv4 → conv5 → pool2
（见 `bsn.py:136-143`，**conv2 在 pool1 之前**），长度
3000 → 750 → 188 → 31 → 31 → 31 → 31 → 7（flatten 7×64 = 448，与 `flat` 声明一致）。

| 层 | 配置 | 输出长度 | MACs/序列 | 占比 |
|---|---|---|---|---|
| conv1 | 1→64, k19 s4 p9 | 750 | 18.24 M | 7.5% |
| **conv2** | 64→64, k11 s4 p5 | 188 | **169.41 M** | **69.5%** |
| conv3 | 64→64, k7 s1 same | 31 | 17.78 M | 7.3% |
| conv4 | 同 conv3 | 31 | 17.78 M | 7.3% |
| conv5 | 同 conv3 | 31 | 17.78 M | 7.3% |
| LSTM | 448→64, T=20 | — | 2.62 M | 1.1% |
| linear | 64→5 | — | 0.0003 M | ≈0% |
| **合计** | | | **243.60 M** | 100% |

CNN 合计 **98.9%**，LSTM 仅 1.1% —— 本质是 CNN 负载，"序列模型"名不副实。

### 3. 总账与效率

- 单序列 fwd ≈ 0.487 GFLOP；fwd+bwd ≈ **1.462 GFLOP**
- 单训练 epoch = 39,527 × 1.462 GFLOP = **57.79 TFLOP**
- 单折（200 epoch）= **11.56 PFLOP**；10 折 = **115.6 PFLOP**（不含 MC 推理）
- 实测吞吐 = 57.79e12 / 47.2 = **1.22 TFLOPS** = 峰值的 **24%**
- 理论地板（100% 效率）= 115.6e15 / 5.03e12 = **6.4 h**
- 实测训练净耗时 ≈ 10 × 200 × 47.2 s = 94,400 s = **26.2 h**
  （总墙钟 31.0 h，差额是 MC 推理 / UGAL 两阶段）

只有 24% 效率的原因（**不是算术受限**）：

1. TU116 无 Tensor Core，只能 fp32；conv2 仅 64→64 通道 + k=11，算术强度低，**访存受限**；
2. BN / ReLU / MaxPool 是纯访存算子，耗时不贡献 FLOPs；
3. 旁证：训练中 `nvidia-smi` 显示 **util 84%、功耗 116.76 W / 125 W（93%）**
   —— GPU "忙"但在等内存与指令发射，不在算 FMA。

### 4. 反直觉的实测佐证：删掉一整个专家只快 5%

| 配置 | 模型数 | 每折耗时 |
|---|---|---|
| 主任务 | 2 | ≈166 min |
| 消融 w/o ensemble | 1 | ≈157 min（仅快 **5.4%**） |

原因在 `run.py:337`：

```python
shards = np.array_split(ids_all[perm], cfg.models)
```

数据被**切分**给各专家（2 专家 × ~19,764 序列 ≈ 1 专家 × 39,527 序列），
每 epoch 总样本吞吐不变 ⇒ **瓶颈是"每样本的 CNN 计算"，与模型个数无关**。

### 5. 若真要提速（按收益排序）

| 手段 | 预期 | 代价 |
|---|---|---|
| **缓存逐 epoch 卷积特征**（CNN 只算 1 次而非 20 次） | 理论 **≈17×** | 改架构；需重定义 BN / dropout 语义 |
| seqlen 20 → 5 | 计算量 ÷4 | 精度下降，偏离论文设置 |
| 削减 conv3–5（各 7.3%，合计 22%） | ≤22% | 偏离论文 |
| 换 30/40 系 + TF32/bf16（AMP） | 理论 5–10× | 换硬件；注意 TU116 的 cuDNN fp16 旧坑 |
| 增大 micro-batch | 有限 | 6 GB 已到上限（micro=128 ≈ 2.69 GB） |

**结论**：这份"小数据集"的 26 h，**20 倍来自算法把每个 30 s epoch 重复卷积 20 次，
4 倍来自 6 GB 无 Tensor Core 显卡的访存瓶颈**。两者相乘解释了几乎全部耗时。

- 注：论文自身标注不一致 —— 双向 LSTM 输出应为 128 维，与 `[BS,64]`、`FC(64→5)` 冲突；
  说明表格文字可疑，但按字面要求，本复现是**单向**。

**B3. BatchNorm 统计量的批次口径**

- 论文 mini-batch = 1024。
- 本复现：micro_batch=128 + 梯度累积 8 → **梯度**等价 1024，但 **BN 的均值/方差是按
  128 个样本（×20 段 = 2560 段）统计的**，不是 1024。
- 6 GB 显存放不下 batch 1024 的激活，属被迫近似。z-score 的 `norm_stats` 已在
  有效 batch 上聚合（对齐论文口径），但 BN 本身未对齐。

**B4. 先验宽度：σ_p 与论文不符（约差 20×）**

- 论文 §IV-B：*"an independent zero-mean Gaussian prior … p(w)=N(0,σ_p²) with σ_p = 1.0"*
- 本复现：`prior_rho = -3.0`，而代码把该值同时用作**先验**与后验初始化
  （`bsn.py:71` `prior_w_rho = full(prior_rho)`）→ 先验 σ_p = softplus(−3) + 1e−6 ≈ **0.0486**
- 沿用了发布代码（`model.py:57` `prior_w_sigma=-3`，第 71 行写入 `prior_w_rho`）。
  （标准 Bayes-by-Backprop 里 ρ=−3 是**后验**初始化，先验固定 σ=1.0；此处把两者混用了。）
- 影响估计：KL 权重仅 2e-8，KL 项 ≈1e-4 量级 vs CE ≈0.2 → 应在噪声级，但口径确实不符。

**B5.（第十五节新发现）原始代码从不切换 train/eval 模式 —— 推理时 BN 也用 batch 统计量**

对全项目 `*.py` 检索 `.eval()` / `.train()`：`model.py`、`tools.py`、
`train-pretrained-model.py`、`test-pretrained-model.py`、`train_active_learning.py`
**没有任何一处调用**（命中的全部在 `repro/` 我自己的脚本里）。
`nn.Module` 默认 `training=True`，因此原始代码**从头到尾处于训练模式**：

- BN 层永远使用 **batch 统计量**，连推理时也是（`model.py:237 influence` 也不调 `self.eval()`）；
- dropout 靠 `forward(x, train=False)` 这个**形参**控制，与模块模式无关
  （`model.py:199-203` / `218-222` / `227-231`：`if train: drop else: if mc_drop: drop`）。

**后果（两层）**：

1. **共享 BN 在原始代码里不会致命** —— running stats 用不上，自然不会出现
   "一套统计量服务不了 5 层"的崩塌。第十五节的配置 B 之所以崩到 31%，
   是因为它把「共享 BN」和「我的 `influence` 会调 `self.eval()`」混在了一起，
   而这个组合**在原代码中不存在**。
2. **推理是"批次相关"的**：测试集的预测取决于同批次样本的统计量，
   等价于一种轻度的 transductive 行为，理论上**可能抬高**论文数字。

**本复现的处置**：`repro/bsn.py` 保留了 `self.eval()`（工程上更规范，且是我们所有数字的
实际口径），并已新增 **`--infer-bn {running,batch}`** 开关以便对齐原始代码。

**→ 已实测结案（2026-09-24，见第十五节第 11-12 小节）**：忠实对齐后结果与我们的基线几乎
完全相同（B′ − A = **+0.02 ACC / −0.67 MF1 / −0.0072 κ**，全在噪声内），
"只换推理口径"单独也无方向一致的收益（A′ − A = +0.48 ACC / −0.30 MF1）。
⇒ 本条**不构成差距来源**；同时它揭示了原代码共享 BN 之所以无害，正是因为它从不切 eval。

   **原代码中不存在的组合**，与"BN 共享"本身无关。
4. ⇒ **第十三节 B5 所涉全部问题排除**。**C（sigmoid 口径）成为目前唯一有实测信号的候选**。
